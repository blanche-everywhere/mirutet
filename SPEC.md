# ミルテト フィネス編 (Miru Tet: Finesse Edition) — SPEC

Endless block-stacking finesse (操作最適化) trainer. Desktop browser only, keyboard only, Japanese UI.
Deliverable: self-contained static app, works from file:// with NO external resources (no CDN, no web fonts, no fetch/XHR of local files, no ES-module imports from file:// — use plain classic scripts / inlined code).
No copyrighted characters or official Tetris assets/logos. Title: 「ミルテト フィネス編」. The mascot is original.

## Rules compliance: Tetris Guideline ("World rule") — STRICT
1. Playfield 10 wide, 40 rows tall internally (rows 0-39, y up), 20 visible (rows 0-19); pieces spawn in rows 21-22 (1-indexed, i.e. the two rows just above the visible field; internal y=20,21). Spawn orientation 0 ("flat side down"): 
   - I: horizontal in the upper of its 4x4 box, occupies columns 4-7 (1-indexed 4..7 => x index 3..6), spawn row 21 (1-indexed).
   - O: columns 5-6 (1-indexed; index 4,5), rows 21-22.
   - T, S, Z, J, L: 3x3 box, columns 4-6 (1-indexed; index 3..5), flat part on row 21, bump on row 22 (T/S/Z point up; J/L: J has the single block top-left, L top-right as in guideline).
   Document the exact coordinates in code comments and test them. Guideline: after spawn, piece drops one row immediately if free — implement as an option `spawnDrop` (default OFF in drill because gravity is off; keep logic + test).
2. Rotation: SRS. CW/CCW use the standard SRS wall-kick tables, with the SEPARATE I-piece table, O has no kicks (O rotation = no-op placement-wise, but it still is a legal "rotation" that changes nothing visible; treat rotation states of O as equivalent). 180 rotation: implement as a setting (default ON) using the TETR.IO 180° kick table (SRS+ 180 kicks) as faithfully as you know it, consistently, documented in code; test that every 180 kick test with an empty board near walls/floor yields a legal result and that 180 equals two sequential rotations when no kick needed.
   Rotation state naming 0,R,2,L. Include full kick data verified by tests against the published SRS tables (write the table literally in the test file from the standard Tetris Guideline / SRS table, independent from engine's representation, e.g. JLSTZ 0->R: (0,0),(-1,0),(-1,+1),(0,-2),(-1,-2); I 0->R: (0,0),(-2,0),(+1,0),(-2,-1),(+1,+2) etc., y up).
3. Guideline colors: I cyan #00F0F0, O yellow #F0F000, T purple #A000F0, S green #00F000, Z red #F00000, J blue #0000F0, L orange #F0A000 (render with a soft glossy/pastel-friendly shading but keep these hues recognisable).
4. Randomizer: 7-bag (each bag a shuffle of all 7; test that every consecutive 7 aligned draws are a permutation). Injectable RNG (seedable) for tests.
5. Hard drop, soft drop, hold (single hold, can't re-hold same piece until lock — in drill mode see below).

## IRS / IHS / ARE (required by user)
- Setting `irs` (default ON): if any rotate key (CW/CCW/180) is HELD at the moment the next piece spawns — including keys pressed/held during the spawn delay (ARE) — the piece spawns already rotated, applying SRS kicks if needed (if no kick fits, spawn unrotated). Priority if multiple held: use the most recently pressed rotate key. 
- Setting `ihs` (default OFF): hold key held/pressed during ARE or at spawn → hold is performed on spawn (initial hold). See hold semantics in drill below.
- Setting `are` : spawn delay in ms (slider+number, 0–500, default 80). During ARE the next piece is shown in the Next box and the target outline for it is already visible (so IRS can be planned); movement keys pressed during ARE are buffered per DAS rules (DAS charge continues; the piece moves per DAS/ARR immediately on spawn if direction held & charged — modern-client style). 
- Finesse counting: an IRS rotation counts as ONE rotation input, exactly like a normal rotation (a rotate key held at spawn counts as one input for the new piece, even if the physical key-down was before spawn; do not double count). Likewise a direction key already held at spawn counts as one input for the new piece if it causes movement. IHS hold is not a finesse input (but is flagged/recorded).
- Tests: IRS with each of CW/CCW/180 for each piece; IRS with kicks needed (cannot happen on empty spawn but test with a custom blocked board); IRS off → no pre-rotation; ARE timing with injected clock; IRS counted as one input in the finesse accounting; solver treats first rotation from spawn identically (cost 1).

## Input handling (frame-independent, performance.now based)
Implement `InputHandler` (in engine.js) driven by `keyDown(action, t)`, `keyUp(action, t)` and `update(t)`, where t is ms timestamp (real app passes `performance.now()` / KeyboardEvent.timeStamp-corrected; tests pass fake times). Must produce identical results regardless of frame rate (i.e. update(t) processes all DAS/ARR/gravity/soft-drop events that occurred between last t and now, in order, even if multiple ARR steps happen in one frame; if ARR=0 move instantly to wall).
- DAS (ms, 0–500, default 110), ARR (ms, 0–200, 0 = instant to wall, default 0), SDF (soft drop factor: 1–40 where "x times gravity", plus "∞/instant" option = drop to floor instantly without lock; default 40... store sdf as number, 41 or special = instant), DCD (DAS cut delay ms 0–200, default 0: after a rotation/ hard drop/ spawn... define clearly: after a piece is rotated or spawned, DAS auto-shift is paused for DCD ms like TETR.IO). Also a setting for gravity (off by default in drill; if on, "G" slider 0-20; keep simple).
- Left/right priority: pressing the opposite direction while one is held switches direction (most-recent-wins), and releasing the newer one resumes older direction with its charge (modern behavior); DAS charge persists across piece spawns when key held. Document.
- DAS charge: first tap moves once immediately; after DAS ms held, auto-repeat each ARR ms. 
- All settings editable by BOTH a slider AND a number input kept in sync, applied live; "reset to default" button; localStorage persistence (key bindings + settings), with try/catch fallback if localStorage unavailable on file://.
- Lock: in drill, no lock delay needed; piece stays until hard drop (gravity off). With soft drop, piece moves down at SDF rate; no auto-lock. Hard drop locks.

## Keys (all fully rebindable; multiple keys per action allowed; conflict detection with swap/warning; "reset keys" button; key-capture UI "press a key…")
Defaults: move left ←, move right →, soft drop ↓, hard drop Space, rotate CW ↑ and X, rotate CCW Z, rotate 180 A, hold Shift and C, retry (R, restarts current target / "retry same target"), pause Esc. Additionally (bindable): next target/skip (N), open settings (S? choose non-conflicting e.g. Tab is bad—use `,` ), toggle hint (H). Prevent page scroll on arrow/space keys. Use KeyboardEvent.code for bindings (show friendly labels in Japanese UI: e.g. "←", "Space", "Shift(左)").
Left/right Shift distinguished (ShiftLeft/ShiftRight) — allow binding either.

## Finesse solver (the core; must be correct and heavily tested)
On an EMPTY 10-wide board (and generalize to arbitrary board via BFS where practical), for a piece P and a target final placement T = (rotation r, column x of the bounding box, resulting lock cells after hard drop), compute the MINIMUM number of key inputs needed, plus one optimal key sequence (list of actions).
- Inputs counted (cost 1 each): a single tap Left, a single tap Right, a DAS-slide (key held until wall/obstacle) Left/Right (counted as ONE input), rotate CW, rotate CCW, rotate 180 (if 180 enabled; solver option `allow180`). Hard drop is NOT counted. Soft drop is never needed on empty board and is not part of optimal sequences (soft-drop key use during a drill counts as +1 input per press; see below). Hold not counted.
- Model: BFS/Dijkstra over states (x, y, rot) on the board starting at spawn state at spawn height (gravity off; rotation uses full SRS kicks with real collision against walls/stack, so wall kicks are modeled, e.g. I vertical against walls, kicks that shift columns). Moves: ±1 (tap), slide to extreme (DAS; moves as far as possible), rotations. Target match = set of lock cells after hard drop equals target cells (this makes symmetric states equivalent: O in any rotation, I rot 0 vs 2, S/Z rot 0 vs 2, etc. — "correct handling of symmetric orientations": rotation states with identical lock cells after dropping are interchangeable; the solver returns min over all equivalent states).
  IMPORTANT: DAS-slide state is a legal move at any time, and rotations may occur at any point in the sequence (before/between/after moves) – BFS covers this. Also allow IRS as first rotation (same cost).
  Since pieces drop to floor only at hard drop on an empty board and gravity is off, y stays at spawn height during BFS; but implement y-aware for generality (soft-drop-based sequences are out of scope for the empty-board optimal tables but the solver API takes a board and may include `softDropTo` moves only if the board has overhangs — OPTIONAL, document if omitted).
- Produce a human readable key sequence like ["DAS←","CW"], or ["→","→","CCW"], rendered in the UI with key caps using current bindings (e.g. "← DAS" ). Prefer canonical optimal sequence ordering: rotation first then movement (it's what guideline tables do), deterministic tie-breaking.
- Reference check in tests: independently hard-code the well-known 2-step guideline finesse maximums/expected counts for notable cases and check solver agrees, e.g.: 
  * O: columns: x=0 (left wall): 1 (DAS ←); 1: 2 (←←? ... check: from spawn col 4-5, going to cols 1-2 needs... compute independently via a SIMPLE separate brute-force implementation in the test (naive BFS written differently, e.g. exhaustive iterative-deepening search over input sequences up to length 6 simulating pieces with its own tiny kick table reading) and compare EVERY piece × EVERY legal (rotation, column) placement on the empty board. Also assert the max optimal input count over all placements per piece ≤ the published guideline bounds (I ≤ 3? check by brute force and report the table in README), that optimal count never exceeds: tap/DAS-bounded e.g. any horizontal-only placement ≤ 3 etc. Also assert known cases: T flat at far-left needs DAS (1); T pointing down (rot 2) at far-left: 2 (rotate 180 or CW,CW if 180 disabled → 3? check by brute force), I vertical at left wall column 0 etc. Print the full table as test output / write it to `tests/finesse-table.txt`.
  * Number of distinct placements on empty board must be: O 9, I 7+10=17, S 7+8=15, Z 15, T 8+9+8+9=34, L 34, J 34 (total 17+... verify: I 17, O 9, S 17? S/Z: flat 8 columns + vertical 9 columns = 17; T/L/J: 8+9+8+9=34). Test the exact numbers.
- Also export `finesseFor(piece, targetCells|{rot,x}, opts)` and `allPlacements(piece)`.

## Drill mode (main training)
Single-piece rounds. Each round: a piece spawns (after ARE) and a TARGET OUTLINE (ghost: pulsing dashed outline in the piece color) shows exactly where it must lock. The player moves it and hard-drops. On lock: compare input count to the optimal count; if equal → perfect (finesse OK); if more → finesse fault. If the placement ≠ target → "ミス" (miss): counts as miss, not as finesse fault; round is repeated with same target (or new, per option).
- Target selection: random uniform over all legal placements (column+rotation) of the chosen piece(s). Options: piece filter checkboxes (I O T S Z J L — any subset, practice one piece), column-area restriction (left / center / right / all, or a chosen column range via two number inputs), "weak spot" mode (weights toward placements with higher fault rate from stats; optional but nice), with 7-bag piece order when multiple pieces selected.
- Input counting: count every key-down of move taps, DAS-slides (a held-until-wall slide = 1; detect: a direction key press that results in auto-repeat movement/charge counts 1 total), rotates, soft drop presses (each separate soft-drop key press +1; the faults are flagged), key re-taps. Count keydown events (not repeats from OS auto repeat — ignore `event.repeat`). Moves that did nothing (against wall) still count as inputs (they are wasted).
- Feedback after each lock: count used vs optimal, ✔ perfect / ✖ fault (+extra inputs), show OPTIMAL KEY SEQUENCE with key-cap graphics (using current bindings), and YOUR sequence recorded (e.g. ← ← ← vs ←DAS). Show them in a result panel under/next to the field for ~ until next piece spawns (non-blocking: the drill must flow rapidly; next piece spawns after ARE).
- "Zero-fault mode" (option): on a fault, the piece is reset (same target, same piece, fresh spawn) and the fault is recorded; the placement doesn't count/advance in sprint.
- "Retry same target" (key R + button): reset current piece to spawn for same target. Option "auto-repeat same target after fault".
- Stats (session + persistent total in localStorage): streak (consecutive perfect), best streak, finesse accuracy % (perfect/total placements), faults per piece type (table with bars), attempts per piece, avg inputs vs optimal, PPS (pieces/sec) for the session/sprint, reset stats button.
- Sprint mode: choose 40 or 100 placements (or custom), timer starts on first input of first piece (or at spawn after "Ready-Go"), ends at N correct placements; results screen: time, PPS, accuracy %, faults, faults by piece, best times saved per sprint length in localStorage, mascot comment. Fault in sprint: counted, and with zero-fault option reset.
- Hold in drill: hold key swaps current piece with the held piece (first use pulls next from bag); the new current piece gets a fresh target; counts as skip (not a placement, no stats). Hold is disabled when a single-piece filter is used (shown disabled, with note). IHS applies at spawn. 
- Pause (Esc) with overlay; the overlay has resume/quit; settings accessible from pause and from main screen.
- Next queue shows 5 upcoming pieces; hold box. Board shows 10x20 visible plus a hint of the spawn rows (rows 21-22 drawn above, dimmer, so spawn position is visibly guideline-correct).
